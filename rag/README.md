# RAG 语料库与提示词

对应任务书 5.2「**RAG 语料库：根据提供的 skill.md 生成的语料库，以及用于构建 RAG 助手的提示词**」。

> ⚠️ **关于 skill.md**：交付时项目内并未找到该文件，也未收到其他说明。
> 因此这里**没有**按某个未提供的规范生成，而是直接以**项目自有知识**为源
> （病害知识库 + 项目文档 + 高频问答）定义了语料 schema 与提示词。
> 若后续拿到 skill.md，只需按其中字段调整 `build_corpus.py` 的输出结构，
> 提示词与检索层不需要改。

## 1. 目录结构

```
rag/
├─ build_corpus.py          # 构建语料（可重复执行，输出覆盖写）
├─ retrieve.py              # 检索 demo（TF-IDF 基线，离线可跑）
├─ corpus/
│  ├─ corpus.jsonl          # 语料（225 块，138 KB）
│  └─ stats.json            # 构建统计
├─ prompts/
│  ├─ system_prompt.md      # 系统提示词（角色 / 硬性约束 / 输出格式 / 示例）
│  └─ user_template.md      # 用户消息模板 + 拼接规则 + 组装伪代码
└─ README.md                # 本文件
```

## 2. 语料构成

| 来源 | 块数 | 内容 | 为什么收录 |
|---|---:|---|---|
| `disease_knowledge.json` | 64 | 38 类病害，每类拆「症状与病因」「防治与用药」 | 用户提问通常只涉及其中一面，拆开检索更准 |
| `docs/*.md` | 149 | 项目文档按标题切块（≤800 字） | 让助手能回答"系统能力边界""数据从哪来"这类问题 |
| FAQ（`build_corpus.py` 内手写） | 12 | 高频问题：上传要求、置信度含义、非叶片提示、精度落差、导出、浏览器… | 这些内容在文档里分散，但用户问得最多 |
| **合计** | **225** | 平均 186 字/块 | — |

**两条构建规则**（都是被实测逼出来的）：

1. **剥离代码块**：命令行片段会引入大量噪声 token，还容易让"部署命令"匹配到"病害症状"。
2. **剔除表格占比 ≥60% 的块**：Markdown 表格切块后是 `| 32 | 番茄 | 番茄叶霉病 |` 这样的碎片，
   既读不通，又因密集出现病名而**把真正的知识块挤出结果**——
   实测"番茄叶子有褐色斑点"的第二名一度被数据库表结构抢走。

## 3. 块结构（schema）

```json
{
  "id": "disease:Tomato___Late_blight#symptom",
  "source": "disease_knowledge.json",
  "kind": "disease",
  "title": "番茄晚疫病 · 症状与病因",
  "text": "叶片出现水渍状暗绿斑……",
  "meta": { "class_id": 30, "crop": "番茄", "healthy": false }
}
```

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一；`disease:<类目录名>#<段>` / `doc:<文件名>#<序号>` / `faq:<序号>` |
| `kind` | `disease` / `doc` / `faq`，便于按类型过滤或加权 |
| `meta.class_id` | 与模型输出索引对齐，可把「识别结果」直接映射到对应知识块 |

## 4. 使用方式

### 4.1 构建

```cmd
py -3.12 rag/build_corpus.py
```

### 4.2 检索（验证语料质量）

```cmd
py -3.12 rag/retrieve.py "番茄叶子有褐色斑点是什么病"
py -3.12 rag/retrieve.py "为什么田里拍的照片认不准" -k 5
py -3.12 rag/retrieve.py "系统怎么启动" --json
```

实测效果：

| 问题 | Top-1 | 相似度 |
|---|---|---:|
| 番茄叶子有褐色斑点是什么病 | 番茄叶霉病 · 防治与用药 | 0.187 |
| 为什么田里拍的照片认不准 | FAQ「模型准确率 99% 为什么认不准」 | 0.451 |

### 4.3 接入大模型

1. 用 `retrieve.py` 的 `Retriever` 取 3~5 条片段（相似度 <0.05 的直接丢弃）；
2. 按 `prompts/user_template.md` 模板 A 拼成 `user` 消息；
3. `system` 消息放 `prompts/system_prompt.md` 全文；
4. 调任意 OpenAI 兼容接口。

组装代码见 `user_template.md` 末尾。

## 5. 设计取舍

| 决策 | 理由 |
|---|---|
| 用 TF-IDF 而非向量检索 | 本机拉不到 embedding 模型（GitHub/外网受限）；字符级 2~3-gram 免分词、零下载。**它作为基线足够**——召回失败恰好说明语料缺内容，先修语料再上向量库 |
| 提示词里禁止给具体剂量 | 农业场景下编造用量是实质性风险；剂量属农药标签与植保规范范畴 |
| 检索为空时**不调模型** | 知识库没有的内容，模型一开口就会补，补的内容往往就是编的。直接返回固定话术更安全 |
| 标题在索引里重复一次 | 标题通常是用户提问的浓缩，加权后命中率明显提升 |

## 6. 已知局限

1. **同义表述召回弱**：TF-IDF 只能匹配字面。问"叶子长斑"能命中"病斑"，问"叶片有斑点"可能差一些。
   上向量检索（bge / text2vec）可解，需能拉到模型。
2. **语料只覆盖本项目知识**：农业通识（如土壤、施肥）在语料外，助手会说"资料未涉及"——这是设计意图，不是缺陷。
3. **未做生成侧评测**：目前只验证了检索命中，没有对"回答是否忠实于片段"做自动评测。
   若要做，可用人工标注 30~50 条问答对，按「有无编造 / 引用是否正确 / 是否越界」三项打分。

## 7. 维护约定

- 语料变更后必须重跑 `build_corpus.py`，并抽查 3~5 个典型问题，确认新块没把正确结果挤下去。
- 若发现助手编造药剂信息，先查 `system_prompt.md` 第二节是否被裁剪。
