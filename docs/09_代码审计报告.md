## 二、重点问题详述

### 【P0-1】默认 JWT 密钥硬编码 → 任意账户接管

**问题**：`src/config.py` 在未设置环境变量 `JWT_SECRET` 时，回退到一个**写死在源码里、随仓库分发**的常量：

```python
JWT_SECRET = "dev-only-insecure-secret-DO-NOT-USE-IN-PROD"
```

由于签发与校验都用它做 HMAC-SHA256，**任何读到这段代码的人都能离线伪造任意用户的 token**——不需要知道任何密码。

**实测证据**（用该公开常量手工签发 `{"uid": 1}`）：

```
→ HTTP 200
{"code":0,"data":{"id":1,"username":"farmer01","nickname":"老农", ...},"msg":"ok"}
```

未输入任何凭据，直接读到了 id=1 账户的资料。按此可继续读取其全部识别历史、删除记录、改资料。

**根因**：把"开发方便"与"安全默认"对立起来了——回退默认值让**默认部署即处于可被接管状态**。

**修复**：未设置环境变量时**为本次进程生成随机密钥**，不再存在公开可预测的密钥。

- 不阻断启动，本地开发体验不受影响；
- 代价：进程重启后旧 token 失效需重新登录（开发场景可接受）；
- 生产仍建议固定设置 `JWT_SECRET`。

**回归验证**：用原公开常量伪造 → `401 {"detail":"token 无效或已过期"}`；连续两次独立进程取密钥 ✅ 不同。

---

### 【P1-2】接口限流可被 `X-Forwarded-For` 绕过（双重成因，隐蔽）

**问题**：限流按客户端 IP 计数，而 IP 取自请求头，且**无条件信任**：

```python
fwd = request.headers.get("X-Forwarded-For")
if fwd: return fwd.split(",")[0].strip()   # 攻击者随便填
```

**实测证据**：固定来源连打 65 次 → 第 61 次被拦（`429`）；**每次换一个伪造 XFF → 65 次全程未被拦**。

**⚠️ 隐蔽的第二层成因（修复过程中发现）**：
在应用层改为「默认不信任转发头」后**问题依旧存在**。定位发现 —— **uvicorn 自身默认启用 `ProxyHeadersMiddleware`**，且默认信任来自 `127.0.0.1` 的转发头。它在 ASGI 层**抢先覆写 `scope["client"]`**，因此应用层读到的 `request.client` 已经是伪造值，**应用层无从察觉**。

也就是说：仅改应用层代码**无法修好**这个问题，必须同时调整启动参数。这也解释了为什么"看起来已经修好了"的代码实测仍然可绕过。

**修复**（两层都要做）：

1. 应用层：`TRUST_PROXY` 开关（默认 `0` = 不信任转发头，按真实 TCP 来源计数）；
2. 启动层：命令加 `--no-proxy-headers`（已同步至 README 6.1 与 `docs/04`）。

**回归验证**：伪造 XFF 连打 65 次 → **第 61 次被限流** ✅；混合测试（先带固定 XFF 打 30 次，再不带 XFF 打 35 次）→ 第二阶段出现 5 次 `429`，证明两次都计入了同一真实 IP 桶。

---

### 【P1-3】登录接口无限流 + 时序侧信道

**问题**：限流只作用于 `/predict`，`/auth/login`、`/auth/register` **完全没有限流**；且用户不存在时直接返回，不执行密码校验。

**实测证据**：

| 输入 | 平均响应耗时 |
|---|---:|
| 已存在用户（走 bcrypt） | **330.3 ms** |
| 不存在用户（直接返回） | **6.5 ms** |

**324 ms 的稳定差异**可直接用于枚举已注册用户名，配合"无速率限制"可对 6 位最短口令做在线爆破。

**修复**：

1. 登录 / 注册各加 10 次/分钟 IP 限流（`RATE_LIMIT_LOGIN_PER_MIN`）；
2. 用户不存在时执行一次**等价 bcrypt 计算**（`auth.dummy_verify`），抹平耗时差。

**回归验证**：耗时差降至 **3.5 ms**（噪声范围）；连续错误登录触发 `429`。

---

### 【P1-4】「改密码」契约不一致 → 密码没改、昵称反被清空

**问题**：`ProfilePage.jsx` 发送 `{ password }`，而后端 `schemas.UpdateMeRequest` 期望 `old_password` + `new_password`。字段名对不上 → 后端 `body.new_password` 为 `None` → 落入「只更新昵称」分支 → `db.update_user(uid, nickname=None)` → 执行 `UPDATE users SET nickname=NULL`。

**实测证据**：

```
PUT /auth/me {"password": "brand_new_pw_123"} → HTTP 200 "资料已更新"   ← 假成功
改密后 nickname 由 'audit_probe_...' 变为 None                          ← 昵称被清空
用「新密码」登录 → 401      用「原密码」登录 → 200                       ← 密码根本没改
```

**影响性质**：这不是普通功能缺陷。用户以为自己改了密码（往往是怀疑账号泄露时的处置动作），**实际密码依旧有效、旧凭据仍然可用**，属于**安全误导**。

**修复**：

1. 前端字段名对齐为 `old_password` / `new_password`，并补上「当前密码」输入项（后端本就要求校验旧密码，原前端根本没提供该字段）；
2. 后端 `nickname` 为 `None` 时**保留原值**，避免任何调用方不小心清空昵称。

**回归验证**：新密码可用 = `True`、旧密码可用 = `False`、昵称保留 ✅。

### 【P1-5】匿名上传文件永久落盘、无清理（待决策）

**问题**：`/predict` 是公开接口（设计如此），但 `(UPLOAD_DIR / save_name).write_bytes(raw)` 位于**鉴权判断之前**，且系统中**不存在任何清理逻辑**（全仓检索 `unlink`/`rmtree`/TTL 仅命中调用点，无清理任务）。

**影响**：匿名用户（未登录）可持续上传文件塞满磁盘。结合 P1-2 的限流绕过，速率几乎不受约束。实测当前目录已有 41 个文件 / 6.3 MB，且只增不减。

**建议方案**（未实施，涉及删除文件，需你确认）：

- 方案 A：启动时清理「无任何数据库记录引用 **且** 修改时间超过 24 小时」的孤儿文件（保守，不会误删有效数据）；
- 方案 B：为匿名上传单独设置更严限流 + 目录总容量上限；
- 方案 C：匿名请求识别后不落盘（仅入库记录的图片才保留）。

推荐 **A + C** 组合。

## 三、P2 项说明（已修部分）

### ✅ P2-6 torch.load 反序列化风险

`torch 2.5.1` 的 `torch.load` 默认 `weights_only=False`，会对权重文件执行完整 pickle 反序列化——**一旦权重文件被替换即可导致任意代码执行**。

修复为 `weights_only=True`。过程中发现本项目 checkpoint（`best/last_resnet18_38.pth`）内嵌了训练脚本写入的 numpy 数值标量（`val_f1` 为 `np.float64`），需显式放行这些**纯数值类型**（`numpy.core.multiarray.scalar`、`numpy.dtype`、`numpy.dtypes.Float64DType` 等）——它们不含可执行代码，放行不引入 RCE 风险。实现为 `_load_checkpoint()`，并对不兼容的第三方权重保留「降级 + 告警」兜底，避免因加固导致模型加载失败。

（`pruned_resnet18_38.pth` 本身不含此类对象，可直接安全加载。）

> 长期建议：训练脚本保存 checkpoint 时把 numpy 标量转为 Python 原生 `float`/`int`，即可完全启用安全加载。

### ✅ P2-7 错误信息泄露

原：`return _err(500, f"识别失败：{e}", 500)` —— 把内部异常原文回传客户端（可能含服务器路径、库版本）。现改为记入服务端日志、对外返回通用文案。

### ✅ P2-8 安全响应头

新增中间件统一注入（实测已生效）：

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'
```

> CSP 收紧到 `default-src 'none'` 的依据：本服务只返回 JSON / 文件流，不承载任何页面。

### ✅ P2-9 PIL 解压炸弹

Pillow 默认 `MAX_IMAGE_PIXELS ≈ 0.89 亿`，且**仅在超过 2 倍时才抛错，中间地带只告警**——一张 10 MB 的高度压缩 PNG 可解压出数百 MB 位图。现显式设为 **5000 万像素**（远超 224×224 输入所需），超标直接拒绝。

## 六、给后续开发的提示

1. **`--no-proxy-headers` 不是可选项**。这是本次审计最隐蔽的一处：代码层面写得再对，只要漏了这个启动参数，限流就形同虚设。若将来部署到 Nginx 之后，才改为 `--proxy-headers --forwarded-allow-ips="代理IP"` 并设 `TRUST_PROXY=1` —— 两者必须**成对**出现。
2. **前后端契约变更必须端到端验证**。本次 P1-4 与 M5 阶段的「识别结果页空白」「历史页分页解析错误」是同一类问题的第三次重演：**mock 会掩盖契约不一致**。建议每次改动契约后，用真实后端跑一次关键路径。
3. **安全默认值优于便捷默认值**。P0-1 的教训是：任何"缺省回退到某个固定密钥/口令"的设计，在生产上都是可被接管的入口。
